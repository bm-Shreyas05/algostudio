# 04 — Intermediate Representation

*(Deliverable J; §27 of the brief)*

---

## J.1 Challenge to the brief

The brief specifies an IR sitting between the AST and the execution engine. I want to be
precise about what the IR is *for*, because the obvious reading — "lower Python to an IR,
then execute the IR" — would mean **writing an interpreter**, which §14 correctly warns
against and which would cap the supported language subset at whatever we manage to
implement.

So: **AlgoStudio's IR is an analysis and description IR, not an execution IR.** Programs are
not executed from it. It sits *beside* the execution path, not inside it:

```
Source ──parse──► AST ──┬──lower──► IR ──► static analysis, source map, capability report,
                        │                  algorithm-pattern detection, AI context, UI outline
                        └──transform──► Instrumented AST ──compile──► executed by CPython
```

This is a deliberate deviation from the brief's diagram and I think it is the right one.
Justification:

1. **Semantics stay free.** CPython executes real Python. We never have to re-implement
   generators, descriptors, MRO, or `int` arithmetic. The alternative loses correctness for
   generality that we do not need.
2. **The IR still does the job the brief wants it to do.** The reason the brief wants an IR
   is language independence — a shared vocabulary so a C++ frontend and a Python frontend
   agree. That agreement is needed at two points: (a) the **event stream** (runtime) and
   (b) a **structural description of the program** (static). The event stream is the
   runtime IR. This document defines the static one.
3. **It costs almost nothing.** The lowering is a few hundred lines and immediately pays
   for itself: the capability report, the static analysis panel (§25), the loop/function
   outline in the UI, and the AI's structural context all read the IR rather than
   re-walking a Python AST — which is exactly what makes them language-independent.

If a future language cannot be instrumented in-process (C++), the IR becomes more load
bearing: the frontend lowers to IR, and a source-to-source instrumenter emits probes from
the IR rather than from a language-specific AST. The design supports that without change.

## J.2 IR node set

Deliberately small. It represents what is needed to *describe* and *visualize*, not to
optimize.

```
Module(body: [Stmt], name)

# --- statements
Assign(targets: [LValue], value: Expr, loc)
AugAssign(target: LValue, op: BinOp, value: Expr, loc)
Delete(targets: [LValue], loc)
ExprStmt(value: Expr, loc)
If(test: Expr, then: [Stmt], orelse: [Stmt], loc)
Loop(kind: for|while, var: LValue?, iter: Expr?, test: Expr?,
     body: [Stmt], orelse: [Stmt], loop_id, loc)
FuncDef(name, params: [Param], body: [Stmt], func_id, is_recursive: bool, loc)
ClassDef(name, bases: [Expr], body: [Stmt], loc)
Return(value: Expr?, loc)
Break(loop_id, loc) / Continue(loop_id, loc)
Try(body, handlers: [Handler], orelse, finalbody, loc)
Raise(exc: Expr?, loc)
Unsupported(reason: str, original_kind: str, loc)     # explicit, never silent

# --- expressions
Const(value, type_tag)
Name(id, ctx: load|store|del, scope: local|global|builtin|unknown)
BinOp(op, left, right)          op in + - * / // % ** << >> | & ^ @
UnaryOp(op, operand)            op in - + ~ not
Compare(op, left, right)        op in < <= > >= == != is is-not in not-in
BoolOp(op, values)              op in and | or
Subscript(container: Expr, index: Expr, ctx)
Attribute(object: Expr, name, ctx)
Call(func: Expr, args: [Expr], kwargs: {str: Expr}, call_id)
MakeCollection(kind: list|tuple|dict|set, elements)
Comprehension(kind, element, generators)
Slice(lower, upper, step)
Lambda(params, body)
IfExp(test, body, orelse)
```

Notes:

- **`Unsupported` is a first-class node.** Lowering never fails; it *marks*. A program
  containing `async def` lowers with an `Unsupported(reason="async functions are not
  instrumented", ...)` node, and the capability report surfaces exactly which line. This is
  the structural mechanism behind §45's "fail gracefully" requirement — the system knows
  what it doesn't know, and can say so at a source location.
- **`loop_id`, `func_id`, `call_id`** are assigned during lowering and are the *same* ids
  the instrumented code emits at runtime. This is the join key between static structure and
  the event stream, and it is what lets the UI say "loop at line 7 ran 12 times" or
  "this call site produced these 3 frames" without any pattern matching.
- **`scope`** is resolved statically (a simple binding pass over each function body:
  assigned names are local unless `global`/`nonlocal`), so the event stream's `scope` field
  can be cross-checked and so the AI context can distinguish a global read from a local one.
- **`is_recursive`** is computed by call-graph SCC detection on the IR. It drives the UI's
  decision to offer a call-tree view before the program even runs.

## J.3 Cross-language mapping (the reason it exists)

| Concept | Python | C++ | Java | JavaScript | IR node |
|---|---|---|---|---|---|
| counted loop | `for i in range(n)` | `for(int i=0;i<n;i++)` | same as C++ | `for(let i=0;i<n;i++)` | `Loop(kind=for, var=i, iter=Range(0,n,1))` |
| collection iteration | `for x in xs` | `for(auto& x: xs)` | `for(T x: xs)` | `for(const x of xs)` | `Loop(kind=for, var=x, iter=Name(xs))` |
| indexed write | `a[i] = v` | `a[i] = v` | `a[i] = v` | `a[i] = v` | `Assign([Subscript(a,i,store)], v)` |
| method mutation | `xs.append(v)` | `xs.push_back(v)` | `xs.add(v)` | `xs.push(v)` | `Call(Attribute(xs, "append"), [v])` normalized to canonical op `list.append` |
| swap | `a[i],a[j] = a[j],a[i]` | `std::swap(a[i],a[j])` | manual temp | destructuring | lowered identically; the **swap lifter** works on the event stream, so all four produce `ALGORITHM_EVENT(swap)` |

The last row is the important one. Normalization does not have to be perfect at the IR
level, because the semantic layer works on **runtime events**, which are already
language-neutral. The IR only needs to be good enough for *static description*. That is a
much weaker requirement than a compiler IR, and it is why this design is achievable by a
student team.

`Call(Attribute(x, "append"))` is annotated during lowering with a `canonical_op` drawn
from a small table (`append/push/push_back/add -> COLLECTION_APPEND`, `pop/popleft/shift ->
COLLECTION_POP_*`). That table is the language-specific part; the IR node is not.

## J.4 What the IR buys, concretely

| Consumer | Uses |
|---|---|
| **Capability report** | walks for `Unsupported` nodes; produces the per-line diagnostics shown in the editor gutter |
| **Static analysis panel** (§25) | function list, loop nest depth, recursion flags, data structures constructed, max nesting |
| **Algorithm pattern detection** (§25, enhancement) | matches structural signatures against the IR — e.g. *while loop whose test compares two variables, body assigns `mid = (lo+hi)//2`, three-way branch on a subscript comparison* -> "looks like binary search, confidence 0.8". Advisory only; it biases view selection and the AI's opening explanation, and is never required |
| **Source map** | `loop_id`/`func_id` -> source ranges, so timeline rows highlight the right span |
| **AI context** | a compact structural summary is far cheaper in tokens than raw source and is language-neutral |
| **Instrumentation planning** | the transformer consults the IR's scope resolution to decide `_as_store` vs `_as_sync` |

## J.5 Explicit non-goals for the IR

- No SSA form, no basic-block CFG, no type inference, no dataflow lattice. If we later want
  "which write produced this value", the *event stream* answers it exactly and at runtime,
  which is strictly better than a static approximation.
- No IR-level optimization. Nothing consumes the IR for code generation.
- No requirement that the IR round-trips to source.
